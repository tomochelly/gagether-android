# 게임별 독립 갱신 · 2026-10-25

## 운영 구조

공개 사이트·D1·R2와 기존 편집/업데이터 권한은 유지한다. 등록된18게임 각각에 방송, 공지, PV, 상세 자료의 독립 작업을 둔다(72개). 유출 자료는 별도 전체 유지보수 작업1개다. 진행 체크포인트, HTTP 단계 잠금, 실행 주기와 출처 건강 기록은 모두 작업 키로 분리하며 스키마 변경은 없다. 한 게임의 실패나 상세 작업은 다른 게임의 빠른 수집 잠금을 점유하지 않는다.

- 방송:2분 목표. 저장된 예약/진행 방송의 확인된 channelId를 먼저 재확인한다. 공식 채널 목록은 새 예약/LIVE 후보를 우선하고 최근 일반 후보2개도 확인한다. 실제 player metadata만 상태 근거로 쓴다. 이미 종료가 확인된 영상의 재검사는6시간 캐시를 사용한다. 알 수 없는 상태나 차단을 종료로 간주하지 않는다.
- 새 공지·PV:3분 목표. 공지는 한국어→기존 피드→같은 게임의 지역 원문→최신 읽을 수 있는 본문 순서다. PV는 독립 official-upload 단계다. 날짜·실제 서비스·원어·검증/최초발견 시각 구분과 owner override를 유지한다.
- 상세:30분 목표. 본문, 추가 게임 정보, 원본 이미지 보완, NTE 프로필, 명조 무기/레퍼런스, 방송 설명문, 외부 도감 수집 영수증을 게임별로 나눠 처리한다. NTE 프로필은2출처씩 체크포인트에 저장한다.17게임의 실제 전체 도감 외부 파서는 기존 별도6시간 수집 작업을 유지한다.
- 각 단계는 선택 게임의 SQL 데이터를 읽는다. 원문 수집의 collection projection은 계속 읽기 전용이다. 저장 전 전체 원본을 다시 읽고 변경 필드를 최신 값에 합친 뒤 payload CAS로 기록한다. 동시에 저장된 다른 본문/언어/가격/null 시각/편집값을 지우지 않는다. 원본·기존 글·이미지·개인 설정·도감 사실 스냅샷은 재작성하지 않는다.

## 호출·인증

GET /api/fast-refresh?plan=1은 등록 작업, 실제 시각, 각 작업의 마지막 시작/완료·진행 결과와 실행 신호를 반환한다. GET/POST ?game=<등록ID>&lane=broadcasts|notices|uploads|details가 각각의 고정 수집기를 선택한다. 유지보수는 game=all&lane=maintenance다. 임의 주소/입력 데이터/삭제는 받지 않는다. 중복·알 수 없는 선택자는 거절한다. POST는 기존 same-origin 검사와 pinned GitHub OIDC 또는 기존 owner/updater 검증을 그대로 요구한다. 공개 쓰기를 열지 않는다.

서버의 runner=fast|details&action=claim|renew|release는 **기존 지정 GitHub workflow의 검증된 run_id**만 운영 임대의 소유자로 사용한다. 임대는12분이며 매 루프 갱신한다.30분 지난 실행은 새 예약 실행이 이어받을 수 있고, 이전 실행은 다음 갱신에서 정상 종료한다. 다른 소유자의 임대를 해제할 수 없다. 저장되는 것은 run_id·서버 시각이며 JWT/서비스 키를 기록하지 않는다.

## 예약 실행과 한계

같은 gagether-refresh.yml의5분 예약은 시작 신호다. GitHub 예약의 지연 가능성은 남는다. 예약으로 시작한 fast 실행은 최대45분 동안 서버 시각 기준으로 **기한이 된 작업만** 확인하며 루프 간60초 대기한다. 실행기당 동시 HTTP 단계4개, 단계별/게임별 저장 체크포인트와8분 wave 예산을 쓴다. 새로운 예약이 겹치면 서버 임대를 확인해 중복 수집 없이 성공 종료한다. 장기 실행은30분 이후 새 예약에 이어지고, 중단된 실행은 임대 만료 후 복구된다. GitHub pending-run 취소를 반복시키는 방식은 쓰지 않는다.

push도 초기 예약 대기 공백을 막기 위해 bounded fast heartbeat를 시작한다. manual은 한 번의 실제 수집 wave를 실행한다. details job은 fast와 독립 실행·임대를 사용한다. 이전 글로벌 POST와12분/240요청 legacy 요청기는 호환·복구용으로 유지한다. 일상 수집은 새 game-refresh-request.py를 사용한다.

이 방식은 GitHub 예약 한 번이 늦어질 때 매 확인 주기가 같이 지연되는 문제를 줄인다. **정확한 실시간/정시 실행을 보장하지 않는다.** 플랫폼 예약·출처 차단·원문 미공개 정보는 별개다. 연결된 시간당 AI 자동화는 기존 일시정지 상태를 보존했으며 새 LLM 자동화를 만들지 않았다.

완료는 실제 persisted readback과 finishedAt을 확인한 경우만 보고한다. 예산 경계 continuation은 저장된 같은 작업의 체크포인트를 다시 확인한 뒤 continuing으로 남긴다. 일부 출처 실패는 게임별 failed/partial로 노출하고 다른 게임을 계속 처리한다. 인증/전송/단계/저장/검증 오류는 실제 실패로 남긴다. UI는 /owner/operations에서18게임×4종류의 상태·마지막 완료·출처 오류·실행 신호를 보여준다.
